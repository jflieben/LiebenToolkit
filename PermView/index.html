Connect to your tenant

Sign in with the account you manage the tenant with. PermView reads Microsoft Graph, Azure Resource Manager, Power BI, Power Platform and Azure DevOps as you. It is read only and changes nothing.

Asked at sign-in:

  • User.Read, Directory.Read.All identity, tenant name and resolving principals; enough for the Administrators view

Asked by popup the first time you run the workload that needs it:

  • Application.Read.All Entra App Access: app registrations, enterprise apps and their API permissions
  • Sites.Read.All SharePoint site
  • Files.Read.All OneDrive
  • Calendars.Read.Shared Mailbox calendar permissions
  • https://management.azure.com/user_impersonation Azure RBAC
  • https://analysis.windows.net/powerbi/api/Workspace.Read.All Power BI workspaces
  • https://service.powerapps.com/User Power Platform environments, plus user_impersonation on the Dataverse instance of a Dataverse environment
  • 499b84ac-1321-427f-aa17-267ca6975798/user_impersonation Azure DevOps

Some of these need admin consent in your tenant. What you see is limited to what your account can read.

PermView is the quick version of a permission audit: top level, one workload and one entity at a time. For audits across every workload, every scope and over time, see m365permissions.com.

Workload

About PermView

PermView gives a quick, top-level view of who has permissions where across the Microsoft cloud workloads you use most. Pick a workload, point it at an entity (a site, mailbox, subscription, workspace, environment) and you get one flat table of principals, roles and scope.

Workloads

  • Administrators: directory roles and their members.
  • Entra App Access: app registrations and service principals with delegated and application API permissions and credential expiry.
  • SharePoint site: app permissions through Graph, plus owners and members of the connected M365 group. The group counts only when its own root site is this site, never on a name match.
  • OneDrive: sharing on the drive root.
  • Mailbox: calendar sharing.
  • Azure: role assignments at subscription scope.
  • Azure DevOps: organisation-level security groups and members.
  • Power BI: workspace role assignments.
  • Power Platform: environment role assignments, or Dataverse security roles for Dataverse environments.

What it does not do

PermView is shallow on purpose. No subsites, libraries, items or mail folders, no resource group RBAC, no project-level Azure DevOps security, no dataset RLS, no app or flow sharing, no PIM eligibility. No history, alerting or scheduled reports either. For a real permissions audit use m365permissions.com.

Hosts it talks to

Tenant data only travels between this page and the Microsoft APIs of the workload you run. Dataverse instance URLs from the Power Platform API are used only when they are https://*.dynamics.com; site URLs only when they are https://*.sharepoint.com.
